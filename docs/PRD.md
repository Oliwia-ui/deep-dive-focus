## 1. Product summary

QuestLog and Deep Dive are two separate personal macOS desktop applications for a student who wants to manage coursework and complete focused study sessions without relying on an internet connection or external account.

- **QuestLog** is a local-first task manager presented as an original enchanted archive. It turns coursework into understandable “quests” while retaining conventional task-management language.
- **Deep Dive** is a local-first focus timer presented as a calm underwater dive computer. Longer planned sessions begin at a greater focus depth, and the diver rises toward the surface as focused time passes.

The applications work independently. When desired, a QuestLog task can be connected to a Deep Dive session by copying its stable task ID and entering it in Deep Dive alongside a readable activity description.

Both applications write append-only Markdown history into separate folders inside one Obsidian vault selected by the user.

## 2. Objective and definition of success

The objective is to deliver two reliable, personal productivity tools that satisfy the assignment’s offline, persistence, timer, task-management, Obsidian, design, and documentation requirements.

The project succeeds when:

1. Both apps remain usable without an internet connection or account.
2. QuestLog supports the full required task lifecycle and retains tasks after restart.
3. Deep Dive supports the full required focus-session lifecycle and records actual focused time rather than assuming the planned duration was completed.
4. Both apps allow the user to select an Obsidian vault and append all required events into predictable Markdown files.
5. Generated vault records include date, time, timezone, event type, status, stable identifiers, and relevant task or session information.
6. The repositories can be installed and run from clean clones using their documented instructions.
7. All submitted sample records were generated by the real applications.

## 3. Intended user and problem

### Intended user

Oliwia Jasionek, a student using macOS for coursework, reading, assignments, and focused study. The apps are personal tools and do not need accounts, collaboration, or multi-user administration.

### Problems

- Coursework can become scattered across generic task lists without enough course context.
- Feature-heavy productivity applications can distract from simply choosing and completing the next task.
- Traditional Pomodoro tools often treat the configured countdown as if it were the actual amount of work completed.
- Cloud-oriented tools can obscure where personal data is stored.
- Task changes and focus history are difficult to reuse in an Obsidian-based study record.

## 4. Product principles

1. **Local authority:** the local data files are the authoritative application state.
2. **Offline operation:** core features require no account or network connection.
3. **Honest history:** planned and actual duration remain separate; cancelled sessions are retained.
4. **Append-only logging:** historical Obsidian events are added rather than silently rewritten.
5. **Playful clarity:** visual personality supports the workflow without hiding familiar concepts.
6. **Personal scope:** optimize for one student on one Mac rather than hypothetical teams.
7. **Reliability before breadth:** required features, testing, and documentation take priority over optional ideas.

# Part A — QuestLog

## 5. Purpose

QuestLog helps the user capture, organize, complete, reopen, and review coursework tasks. Its enchanted-archive presentation makes the experience personal while conventional labels remain visible enough for immediate understanding.

## 6. Core features

### 6.1 Quest lifecycle

The user can:

- Create a quest.
- View active and completed quests.
- Edit an existing quest.
- Delete a quest after confirmation.
- Mark a quest complete.
- Reopen a completed quest.

### 6.2 Quest fields

Each quest contains:

- Stable UUID
- Title
- Optional description
- Course or module
- Optional due date
- Important flag
- Status: active or completed
- Creation timestamp
- Last-updated timestamp
- Optional completion timestamp

### 6.3 Views

- **Active Quests — Tasks:** all open quests.
- **Today’s Journey — Today:** open quests due today, overdue, important, or manually included in the focus queue.
- **Quest Archive — Completed:** completed quests with the ability to reopen them.
- **Settings:** Obsidian vault, local-data information, and logging status.

### 6.4 Filters and search

The user can:

- Search by title or description.
- Filter by course/module.
- Filter by active/completed status.
- Identify due-today and overdue quests.

### 6.5 Cross-app reference

Each quest exposes a copyable task reference containing at minimum its stable task ID and title. Deep Dive can accept this ID, but QuestLog does not require Deep Dive to be installed or running.

## 7. QuestLog custom features

### 7.1 Enchanted Archive

The interface resembles an original magical quest book or living archive, using chapter dividers, book/page surfaces, scroll-like tabs, restrained spirit-light effects, and satisfying completion feedback. It must not reproduce protected franchise characters, logos, names, symbols, or artwork.

### 7.2 Course-aware focus queue

The user can organize quests by course/module and identify a small Today/Focus Queue without needing a large project-management hierarchy.

## 8. QuestLog Obsidian logging

The user selects an Obsidian vault through a native folder picker. QuestLog stores that selected path locally and writes into:

```text
<Vault>/QuestLog/Task History/YYYY-MM.md
```

Required event types:

- `TASK_CREATED`
- `TASK_EDITED`
- `TASK_COMPLETED`
- `TASK_REOPENED`
- `TASK_DELETED`

Each event includes:

- ISO 8601 date, time, and timezone offset
- Event type
- Resulting task status
- Task ID
- Task title
- Course/module when present
- Due date when present
- Changed fields for edits
- A final task snapshot for deletion

A prior event is never removed when the live task changes or is deleted.

# Part B — Deep Dive

## 9. Purpose

Deep Dive helps the user conduct focused study sessions and breaks while maintaining an honest record of planned time, actual focused time, pauses, cancellations, and overtime.

## 10. Core features

### 10.1 Session lifecycle

A focus session follows this state model:

```text
idle → running ↔ paused → completion decision → completed or cancelled
                                      ↘ overtime running → completed or cancelled
```

The user can:

- Start a focus session.
- Pause and resume it.
- Stop and choose whether to complete or cancel it.
- Respond when the planned duration reaches zero.
- Continue focusing in overtime.
- Start and complete a break.
- Review completed and cancelled sessions.

### 10.2 Session fields

Each session contains:

- Stable UUID
- Kind: focus or break
- Status: running, paused, completed, or cancelled
- Activity description
- Optional QuestLog task ID
- Planned duration
- Actual accumulated running duration
- Accumulated paused duration
- Start timestamp
- End timestamp when settled
- Overtime duration when applicable

### 10.3 Duration settings

The user can configure:

- Default focus duration
- Short-break duration
- Long-break duration
- Sound enabled or muted

Suggested defaults are 25 minutes for focus, 5 minutes for a short break, and 15 minutes for a long break.

### 10.4 Review history

The app displays completed and cancelled sessions newest first. Each record shows:

- Activity
- Optional task ID
- Status
- Planned duration
- Actual focus or break duration
- Start and end times
- Overtime when applicable

## 11. Deep Dive custom features

### 11.1 Focus depth

The selected planned duration determines an illustrative starting depth. Longer sessions begin deeper. The interface combines a meter-like gauge with fictional zones such as:

- Shallows
- Reef
- Blue Water
- Twilight
- The Deep

This is a focus metaphor and not real dive-planning guidance.

### 11.2 Ascent visualization

At session start, a brief animation places the diver at the target focus depth. As actual focused time accumulates, the diver rises toward the surface. Pausing also pauses ascent. The timer is calculated from stored timestamps; animation frames are never the authoritative clock.

### 11.3 Surface decision

When planned focus time is reached, the app pauses at the surface and displays:

- **Complete Dive**
- **Start Surface Break**
- **Stay Below**
- **Cancel Dive**

Choosing Stay Below continues actual time in overtime while the diver remains just below the surface and a positive overtime counter is shown.

### 11.4 Completion feedback

The app uses:

- Surface-arrival animation
- macOS system notification
- Quiet original bubble/chime sound
- Mute setting

Reaching zero alone does not mark the session completed.

### 11.5 Honest session receipt

A completed or cancelled session produces a clear receipt containing planned duration, actual running duration, paused duration, overtime, outcome, activity, optional task ID, and timestamps.

## 12. Deep Dive Obsidian logging

The selected vault path is stored locally. Deep Dive writes into:

```text
<Vault>/Deep Dive/Focus History/YYYY-MM.md
```

Required event types:

- `SESSION_STARTED`
- `SESSION_COMPLETED`
- `SESSION_CANCELLED`

Completion and cancellation records include both planned and actual duration. Events also contain:

- ISO 8601 date, time, and timezone offset
- Session ID
- Session kind
- Status
- Activity description
- Optional QuestLog task ID
- Start and end timestamps where applicable
- Planned duration
- Actual running duration
- Paused duration
- Overtime where applicable

Break sessions are stored separately from focus sessions and never count toward focused-study totals.

# Part C — Shared technical and design decisions

## 13. Framework

Both apps use Electron, React, TypeScript, and Vite.

Reasons:

- The required Node.js and Apple tools are already installed.
- Electron provides direct, controlled filesystem access for local storage and Obsidian logging.
- The user is comfortable with React and TypeScript.
- Using the same stack reduces implementation and debugging risk across two repositories.
- Tauri was considered but rejected because Rust is not installed and the deadline does not justify adding another toolchain.

## 14. Local storage

Each app stores authoritative data and settings as JSON under Electron’s application-data directory. Writes use a temporary file followed by replacement where practical.

The selected vault path and pending log retry queue are stored in settings. No cloud service or account is involved.

## 15. Application security boundary

- Renderer processes do not receive unrestricted Node.js access.
- Electron context isolation remains enabled.
- A narrow preload bridge exposes only required operations such as loading/saving app state, selecting a vault, appending logs, notifications, and opening local folders.
- User-provided text is treated as text rather than executable HTML.

## 16. Obsidian write reliability

A successful local mutation and a successful Obsidian append are tracked separately.

If local state saves but logging fails:

1. The local state remains saved.
2. A visible warning identifies the unlogged event.
3. The event enters a persistent retry queue.
4. The app retries when requested or when the vault becomes available.
5. The event is marked logged only after the append succeeds.

Idempotency information should prevent the same queued event from being appended twice during retry.

## 17. Screen layout decisions

### QuestLog

- Left navigation: Active Quests, Today’s Journey, Quest Archive, Settings
- Central quest list or book pages
- Create/edit panel or modal
- Search, course filter, and New Quest action near the top

### Deep Dive

- Central timer, depth gauge, diver, bubbles, and status
- Activity description and optional QuestLog task ID close to timer controls
- Accessible session-history area
- Settings for durations, sound, and vault selection

## 20. Main user flows

### QuestLog flow

1. Open QuestLog.
2. If needed, select an Obsidian vault.
3. Create a quest with title, course, and optional details/due date.
4. View it in Active Quests or Today’s Journey.
5. Edit, complete, reopen, or delete it.
6. Observe the resulting state after restart.
7. Open the monthly QuestLog Markdown file and verify the append-only history.
8. Copy the quest ID when linking it to Deep Dive.

### Deep Dive flow

1. Open Deep Dive.
2. If needed, select an Obsidian vault.
3. Enter an activity and optional QuestLog task ID.
4. Choose or accept a focus duration.
5. Start, pause/resume, and continue the dive.
6. At the surface, complete, begin a break, stay below, or cancel.
7. Review the session receipt and history.
8. Open the monthly Deep Dive Markdown file and verify planned and actual duration.

## 21. Testable acceptance criteria

### QuestLog functional criteria

1. Creating a valid quest makes it visible without restarting.
2. A created quest remains present after closing and reopening the application.
3. Editing a quest persists every changed field after restart.
4. Completing a quest removes it from Active Quests and adds it to Quest Archive.
5. Reopening a completed quest returns it to Active Quests without changing its stable ID.
6. Deleting a quest removes it from live views only after confirmation.
7. Search matches quest titles and descriptions.
8. Course filtering shows only matching quests.
9. Today’s Journey identifies due-today and overdue active quests.
10. A quest ID can be copied with its title.

### QuestLog logging criteria

11. Creating a quest appends one `TASK_CREATED` event.
12. Editing a quest appends one `TASK_EDITED` event containing changed fields.
13. Completing a quest appends one `TASK_COMPLETED` event.
14. Reopening a quest appends one `TASK_REOPENED` event.
15. Deleting a quest appends one `TASK_DELETED` event containing a final snapshot.
16. All events contain timestamp, timezone, event type, status, task ID, and title.
17. Performing create → edit → complete → reopen → delete preserves all five events in order.
18. Selecting a different valid vault redirects future events without overwriting previous history.

### Deep Dive functional criteria

19. Starting a focus session changes state from idle to running and begins actual-time accumulation.
20. Pausing stops actual-time accumulation within an acceptable timer tolerance.
21. Resuming continues from accumulated actual time rather than restarting.
22. Stopping allows the user to complete or cancel instead of silently discarding the session.
23. Reaching the planned duration presents the four surface decisions and does not auto-complete.
24. Stay Below records overtime while preserving the original planned duration.
25. Complete Dive stores a completed session with actual duration.
26. Cancel Dive stores a cancelled session with actual duration.
27. Starting a break creates a distinct break session that does not count as focused time.
28. Configured focus and break durations persist after restart.
29. Completed and cancelled sessions remain visible after restart.
30. Session history shows planned and actual durations separately.
31. A session accepts both a readable activity and optional QuestLog task ID.

### Deep Dive logging criteria

32. Starting a session appends one `SESSION_STARTED` event.
33. Completing a session appends one `SESSION_COMPLETED` event.
34. Cancelling a session appends one `SESSION_CANCELLED` event.
35. Completion and cancellation contain planned duration, actual duration, status, activity, timestamps, and task ID when supplied.
36. Paused time is excluded from actual focused duration and available in the receipt.
37. Overtime is explicitly present when actual duration exceeds planned duration.

### Shared offline and reliability criteria

38. Both apps launch and perform their core functions with network connectivity disabled.
39. Neither app requires account creation or sign-in.
40. Local data survives a complete application quit and relaunch.
41. Obsidian events append to predictable app-specific monthly files.
42. Existing Markdown events remain unchanged after later edits or deletions.
43. If the vault is unavailable, the local mutation succeeds, a visible warning appears, and the event enters a persistent retry queue.
44. Retrying after vault access is restored appends the missing event once.
45. Each repository installs and runs from a clean clone using only documented steps.
46. Automated tests and manual checks pass before submission.
47. Submitted sample Markdown contains records generated by the packaged or development applications, not manually fabricated examples.

## 23. Alternative considered

A single combined task-and-timer application was considered. It would reduce packaging and repository work and allow direct task selection. It was not chosen because the user prefers two distinct personal experiences: an enchanted task archive and an underwater focus environment. Loose coupling through optional task IDs preserves the ability to use them together without making either app dependent on the other.

Tauri was also considered as the desktop shell. Its smaller bundles were attractive, but Electron was selected because the existing environment already supports the complete JavaScript toolchain, direct filesystem integration is straightforward, and installing Rust would increase deadline risk.

## 25. Research ledger

### Established

- The assignment requires complete task CRUD, completion/reopening, persistence, timer controls, breaks, configurable durations, session linkage/context, history, and specified Obsidian logs.
- Cloud-oriented competitors may provide offline modes without making local data authoritative.
- Planned Pomodoro duration and actual tracked duration are distinct in credible time-tracking systems.
- The local environment supports Node.js, npm, Electron development, Git, GitHub, and macOS command-line tools.

### Assumptions

- A JSON dataset is sufficient for one user’s personal tasks and sessions.
- macOS notification permission will be available during testing.
- The selected Obsidian vault will be writable from the Electron application.

### Unresolved implementation risks

- Persistence of macOS folder access and permissions must be tested early.
- Timer recovery after the computer sleeps or the app restarts needs timestamp-based tests.
- Animated visual concepts must remain performant and accessible.
- Packaging behavior from a clean clone must be verified before the deadline.

### Evidence that would change the plan

- If Electron cannot reliably regain access to the selected vault, the vault-selection and permission strategy must change immediately.
- If JSON writes prove unreliable under realistic mutation sequences, storage should move to a local database.
- If the two-app schedule threatens required testing or documentation, optional animation and secondary filters should be reduced before any required behavior is removed.

## 26. Product verdict

**Conditionally supported with high confidence.** The concept is feasible by September 27, 2026 only under the defined narrow scope. The decisive success factors are reliable local persistence, correct timer accounting, verified append-only Obsidian logging, and disciplined small Git commits. Visual personality is valuable, but it remains subordinate to these acceptance criteria.
